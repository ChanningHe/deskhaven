- 2026-11-02, M1-05, write-behind (`persist.rs`; `PeerMap::update_pk` keeps only the call
  site): an accepted RegisterPk updates memory, bumps the peer's generation and is answered
  **OK before it is persisted**. Writes are **coalesced per peer**: the queue holds peer ids,
  each at most once, and one writer task writes the peer's state as it is when written, so
  repeated registrations become one write and the queue never exceeds the number of peers.
  **A store outage keeps devices online** (as upstream, which ignored write errors): a failed
  write re-queues the id and the writer retries it itself (no `request_pk`, nothing asked of
  the client); after 3 consecutive failures a circuit breaker pauses all writes for a
  cool-down (1 s, doubling to 30 s) and then probes with one write; each attempt has a 5 s
  timeout. The queue bound (1024) refuses only ids that are not bound yet (SERVER_ERROR, the
  client retries; detected before memory changes); a bound peer is always accepted. On
  `StoreError::UuidMismatch` (the store binds the id to another device) the store's record is
  re-read into the cached peer in place (rate-limit counter and address kept). On stop the
  writer gives each queued write a single attempt (no breaker, no backoff) within one 5 s
  deadline that covers the in-flight write (`Tasks::spawn_draining`); the number of writes left
  unsaved is logged.

- 2026-11-02, M1-06, relay selection (`rendezvous_server.rs` `get_relay_server`): delegates to

- 2026-11-02, M1-06, serving state (`server.rs`): `SignalHandle::is_serving()` and

  listener is bound and `run` is still running, through a `watch` channel set by
  `RendezvousServer::serve` after binding and reset when `run` returns (a dropped `run` future
  closes the channel, which also reads as not serving). The embedding process gates startup
  and readiness on it.
- 2026-11-02, M1-06, review fixes (`server.rs`, `rendezvous_server.rs`): `SignalServer::run`
  runs the server loop under `catch_unwind`, so a panic no longer skips `tasks.shutdown()` (a
  registration writer still flushing would have raced a restarted instance or the embedder's
  database close); the panic becomes `SignalError::Internal("signal server panicked: …")`,
  which the embedder restarts like any error. The serving flag is reset as soon as the loop
  ends, before the drain, so readiness drops at once. New `SignalHandle::stopped()` resolves
  once `run` has returned (drain included) or its future was dropped. New cargo feature
  `testing` (dev-only for embedders): `SignalHandle::inject_fault(Fault::{Error, Panic})`
  makes the server loop fail through a `Data::Inject` message (compiled only with the feature
  or in this crate's tests).
- 2026-11-02, M1-06, relay list semantics (documented): the initial list of a (re)start uses
  every entry that resolves and retries the others on the timer (M1-03), while a runtime
  update through `SignalHandle::set_relay_servers` is all or nothing (one unresolvable entry
  rejects the update and the previous list stays). The embedder retries a rejected update.
