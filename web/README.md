# deskhaven web console

React + TypeScript + Vite single-page app. It is built to `web/dist` and embedded into the
deskhaven binary by `crates/deskhaven-web` (rust-embed).

## Embedding and release builds

```sh
nix develop -c cargo run -p xtask -- dist   # pnpm install + build, then cargo build --release -p deskhaven
```

- Release builds embed `web/dist`; debug builds read it from disk, so `pnpm -C web build` is enough
  during development (or use `pnpm -C web dev` with the Vite proxy).
- `cargo build` works without `web/dist` (with a `cargo:warning`): the SPA routes then answer 503
  with a "web console not built" page. `crates/deskhaven-web/build.rs` always watches `web/dist`, so
  a later `pnpm -C web build && cargo build --release` re-embeds without `xtask dist`. While
  `web/dist` is missing, that crate is recompiled on every build (cargo treats a missing watched path
  as changed).
- `xtask dist` installs with `--ignore-scripts`: the build does not need dependency lifecycle
  scripts, and a release build should not run third-party install code.
- The server sends a strict Content-Security-Policy (`deskhaven_web::CSP`): scripts and styles must
  be external files from the same origin. No inline `<script>`/`<style>`, no `style=""` attributes,
  no `eval`, no `data:` images. Setting styles through the DOM (`el.style.x`, which is what React's
  `style` prop does) is fine. A change to `index.html` or the build config that breaks this is caught
  by `crates/deskhaven-web/tests/csp.rs`.
- Paths under `/api` and `/admin/api` are never answered with `index.html`; a missing file with an
  extension is a 404. The check runs on the decoded path with empty segments collapsed, so `//api/x`,
  `/admin//api/x` and `/%61pi/x` get a bare 404 too. Only the literal prefixes get the API's JSON
  error shape; these odd spellings do not match any API route and get the bare 404 (acceptable).
- Playwright smoke tests (open the home page against a release binary) are deferred until
  `deskhaven serve` serves the console (M0-09).

## Commands

Run from the repository root inside `nix develop` (provides node and pnpm):

```sh
pnpm -C web install --frozen-lockfile
pnpm -C web dev          # http://localhost:5173, proxies /api and /admin/api to 127.0.0.1:21114
pnpm -C web build        # -> web/dist
pnpm -C web typecheck    # tsc --noEmit (app + node configs)
pnpm -C web lint         # eslint (type-aware) + prettier --check
pnpm -C web test         # vitest + Testing Library (jsdom)
pnpm -C web i18n:check   # fails on keys missing from a locale or {{placeholders}} that differ
pnpm -C web format       # prettier --write
```

The pnpm version comes from the Nix devshell, so `package.json` has no `packageManager` field (it
would make pnpm try to download another version). `pnpm-workspace.yaml` explains its
`minimumReleaseAgeExclude` entries and when to remove them.

`src/routeTree.gen.ts` is generated by the TanStack Router plugin on `dev`/`build`. It is committed so
`typecheck` works on a fresh clone. Never edit it by hand.

## API client

- **Generated.** `pnpm gen:api` runs orval (`orval.config.ts`) on
  `crates/deskhaven-admin-api/openapi.json` (itself produced by `cargo xtask gen-openapi`) and
  writes types and TanStack Query hooks to `src/api/generated`. The output is committed, like
  `routeTree.gen.ts`, and CI fails when it differs from a fresh run. Never edit it by hand; a
  backend change is `cargo xtask gen-openapi && pnpm -C web gen:api`.
- **One fetch wrapper.** Every request goes through `apiFetch` (`src/api/client.ts`, orval's
  mutator). It sends cookies same-origin only, adds `X-Deskhaven-CSRF` (the value of the
  `__Host-deskhaven_csrf` cookie, or a placeholder before login) to every non-GET request, and
  throws `ApiError` for non-2xx responses: `status`, the envelope's `code`/`message`/`details`,
  and `retryAfterSeconds` from `Retry-After`. `ApiError` extends `HttpError`, which the query
  policy below relies on. Response bodies are typed from the OpenAPI document, not validated.

## Data fetching and errors

- **Retries** (`src/app/query-client.ts`): 4xx responses are never retried. Network errors and 5xx
  are retried once.
- **401**: any query or mutation that fails with 401 calls `onUnauthorized`, which `createApp`
  (`src/app/create-app.ts`) wires to: forget the cached session, then redirect to
  `/login?redirect=<current path>`.
- **Error messages** come from `errorMessage(error, t)` (`src/api/error-message.ts`): the API
  error `code` maps to `errors.codes.<code>` (exhaustive over the generated `ErrorCode`, so a new
  backend code fails `tsc` until it is translated), 429 with `Retry-After` says how long to wait,
  responses without a known code fall back to their HTTP status, errors without a status read as
  network failures. The server's English `message` is never shown. `<ErrorAlert>` renders one.
- **Route errors** use the router's `defaultErrorComponent` (translated, with retry and a link
  home); a 403 renders "access denied" without a retry. Slow routes show
  `defaultPendingComponent`. A route only sets its own `errorComponent` when it needs something
  more specific.

## Session and permissions

- The `_app` layout's `beforeLoad` resolves the session with `GET /admin/api/v1/me`
  (`requireSession`, cached for 5 minutes) and passes `me` to every child route; no session (401)
  redirects to `/login?redirect=...`. The login route keeps `redirect` only if it is a same-origin
  path (`safeRedirectTarget`), so it cannot be turned into an open redirect.
- Every page's permission (`self` / `admin` / `owner`, named like the API's security scopes) is
  declared once in `PAGE_PERMISSIONS` (`src/features/auth/permissions.ts`). Each route calls
  `requirePagePermission(context.me.role, '<page>')` in `beforeLoad`, and the sidebar and command
  palette hide pages the role cannot open. Plain users land on `/me`. These checks only shape the
  UI: the server enforces every permission.
- Components below `_app` read the user with `useMe()`.

## Lists (DataTable)

Every list uses `DataTable` (`src/components/common/data-table`, 08 §1.5): server-side
pagination, sorting and filtering, all held in the URL. A list page looks like this:

```tsx
const SORTABLE = ['name', 'last_online'] as const
const column = createDataTableColumnHelper<Device>()
const COLUMNS = column.columns([column.accessor('name', { header: 'Name', meta: { label: 'Name' } })])

// route: validateSearch: (raw) => ({ ...parseTableSearch(raw, { sortable: SORTABLE }), online: ... })
const search = Route.useSearch()
const navigate = Route.useNavigate()
const query = useQuery({ ...devicesQueryOptions(toListParams(search)), placeholderData: keepPreviousData })
<DataTable id="devices" label={t('nav.devices')} columns={COLUMNS} sortable={SORTABLE}
  data={query.data} error={query.error} onRetry={() => void query.refetch()}
  getRowId={(d) => String(d.id)} search={search}
  onSearchChange={(patch) => void navigate({ search: (prev) => applyTableSearch(prev, patch) })}
  searchPlaceholder={...} emptyState={<EmptyState ... />} />
```

- URL keys are the API's list parameters (08 §6): `page`, `page_size` (10/20/50/100/200), `sort`
  (`field` or `-field`, single column, only ids listed in `sortable`), `q`, plus page filters.
  Invalid values are dropped, defaults are omitted, and any change except the page itself goes
  back to page 1 (`applyTableSearch`). Page, sort and filter changes push history entries, so
  the back button walks through them; the search box applies after a 300 ms pause or on Enter.
- Column visibility is a per-browser preference (localStorage), not part of the URL.
- `bulkActions` enables row selection (current page only; a new page, sort or filter clears it).
- With no rows and no filter, `emptyState` replaces the table (08 §4: offer the next step); with
  filters, the table says "no results" and offers to clear them.
- **Not found**: unknown URLs render inside the shell (`_app/$.tsx` passes them to the `_app`
  layout's `notFoundComponent`). The root `notFoundComponent` is the shell-less fallback.

## Layout

```
src/
  app/                 providers, query client, router factory
  routes/              file-based routes, kept thin: they import a page from features/
  features/<domain>/   one folder per domain (devices, users, groups, addressbooks, strategies,
                       audit, auth, client-setup, tokens, settings, overview, shell)
    components/        domain components and the page component
    api.ts             query hooks for the domain (added once the API exists)
  components/ui/       shadcn components (Base UI primitives) only, added via `pnpm dlx shadcn add`
  components/common/   shared app components (PageHeader, EmptyState, DataTable, dialogs, ...)
  api/                 apiFetch, ApiError, error-code messages; generated/ is orval output
  i18n/                i18next setup, locales/*.json, typed resources
  lib/                 framework-free helpers (storage, theme, utils)
  test/                test setup and render helpers
public/theme-init.js   applies the saved theme before first paint (no flash, CSP-friendly)
```

## Conventions

- **Feature folders.** Code for a domain lives in `src/features/<domain>`. A route file in
  `src/routes` only binds a path to a page component.
- **ui vs common.** `components/ui` holds shadcn code only. You may adjust it, but keep it generic.
  Components that know about the app (i18n, routing, domain types) go in `components/common` or a
  feature folder.
- **i18n.** Every user-visible string goes through `t()`. Keys come from `src/i18n/locales/en.json`
  and are type-checked, so an unknown key or a key missing from `zh-CN.json` fails `tsc`. Add every
  key to all locales; `pnpm i18n:check` catches keys that exist in only one of them, and keys whose
  `{{placeholder}}` names differ between locales. Language names
  in the switcher are written in their own language and are not translated.
- **Types.** `strict` plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. No `any`;
  ESLint enforces this.
- **Size.** Components stay under 200 lines. ESLint `max-lines` enforces this for `src/**/*.tsx`
  outside `components/ui`. Split a component before it gets close.
- **Styling.** Use Tailwind utilities and the semantic tokens in `src/index.css` (`bg-background`,
  `text-muted-foreground`, ...), never raw colors. The only inline styles allowed set CSS variables
  (`style={{ '--x': value }}`), and ESLint enforces this.
- **No `console.*`** in app code, enforced by ESLint.
- **Accessibility.** Use semantic landmarks, give icon-only buttons an `aria-label`, keep focus
  visible, and make sure everything works from the keyboard. Each page has exactly one `h1` (the
  `PageHeader` title, or an `EmptyState` with `headingLevel={1}` when the empty state is the page).
  After each client-side navigation, `RouteAnnouncer` moves focus to `<main>`, announces the new
  `h1` and updates `document.title`.
- **Toggles** keep a fixed `aria-label`; only `aria-expanded`/`aria-pressed` reflects the state.
- **Links that look like buttons** are `<Link className={buttonVariants(...)}>`. Base UI's
  `<Button render={<Link/>}>` would turn the link into `role="button"`.
- **Tests.** Write user-level tests with Testing Library (query by role and accessible name).
  `src/test/render-app.tsx` renders the full app at a given path.
- **Persistence.** Read and write `localStorage` only through `src/lib/storage.ts`, which falls back
  safely when storage is unavailable. Keys are namespaced `deskhaven.*`.
